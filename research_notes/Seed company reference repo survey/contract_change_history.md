# Real cross-service contract-change history in public multi-service reference repositories

Method note (applies to everything below): four repositories were cloned (history only) and mined with `git log` on contract paths (`pb/demo.proto`, changelogs, integration-event files); every PR/issue cited was then opened on github.com and its thread read. Commit links come from the clones. 43 examples are catalogued; 38 are in the four priority repositories. Where a review comment's author could not be extracted from the page, it is attributed to "a reviewer". Merge status is stated only where a merge commit or changelog entry confirms it. Repos abbreviated: OB = GoogleCloudPlatform/microservices-demo (Online Boutique), OTel = open-telemetry/opentelemetry-demo, eShop = dotnet/eShop, eSOC = dotnet-architecture/eShopOnContainers.

## What kinds of contract change actually occur? (catalogue of examples, classified)

### Takeaway
Across 43 verified examples the commonest real changes are (a) field type/shape changes in a shared protobuf, (b) renames of things that are not in the IDL at all (package names, service names, env vars, ports, telemetry attribute keys, Kafka topic/consumer settings), and (c) event-schema and delivery-semantics problems on the message bus. Several kinds do not fit the supplied list: namespace/package renames, service/DNS/env-var renames, a service rewritten in another language behind the same contract, generated-code/duplicated-IDL drift, platform API-version removal, and wire-encoding negotiation.

### Cited Findings

Each entry: **ID. title** — repo, link, date; contract; services (languages); what went wrong / was discussed; class; size.

- Kinds that do not fit the supplied list: (1) namespace/package rename (B2); (2) service identity rename covering DNS, image and telemetry names (B6); (3) consumer rewritten in another language behind an unchanged contract (B5); (4) duplicated IDL / generated-code drift and build-context coupling (A10, A11, B4, B21, C5); (5) observability attributes as a contract with dashboards and tests as consumers (B17); (6) platform API-version removal that also adds a required field (E1, E2); (7) wire-encoding negotiation for mixed-version rollout (E4); (8) removal of the last reader of a flag (B19); (9) responsibility moved from one service to another (A4, A6, D6).

- Demo repositories keep all services in one repo, so most contract changes were made atomically in one PR; the "forgotten consumer" cases cluster where the consumer is not compiled against the IDL: config/env vars, proxy templates, flags, tests, dashboards, Helm charts in another repo, and UI paths not exercised by the load generator.

### Gaps
- Online Boutique's 2018 breaking commits predate public PR review, so there is no discussion to quote; ordering is inferred from commit sequence only.

A Backstage issue opened (#9119) turned out to be a dependency-duplication problem, not a service contract, and is excluded.
- GitHub's unauthenticated search API rate-limited the session, so issue searches were keyword-sampled, not exhaustive; counts below are over the catalogue, not over all history.

## How often did a contract change land without one of its consumers being updated, and how was it discovered?

### Takeaway
In 15 of the 43 catalogued examples a change landed (or was proposed) with at least one consumer not updated. Discovery was by a human reviewer running the app by hand (4), CI or test failures after merge (3), user or tester bug reports (5), and later code reading or audit (3); none was caught by a schema-compatibility check.

### Cited Findings
- Caught by a reviewer's manual test before merge: zip-code change missed the frontend shipping-quote path, causing a Rust panic (B1) — [PR #587](https://github.com/open-telemetry/opentelemetry-demo/pull/587)
- Caught by reviewer before merge: enum change missed the DB column at runtime, an integration event's field type, and a CSS class in the web UI (C1) — [PR #151](https://github.com/dotnet/eShop/pull/151)
- Caught by reviewer question: hybrid mobile app endpoints not updated for API versioning (C2) — [PR #390](https://github.com/dotnet/eShop/pull/390)
- Caught by reviewer build + automated review: another service's tests and stale flags after a revert (B19) — [PR #3873](https://github.com/open-telemetry/opentelemetry-demo/pull/3873)
- Caught by CI after merge: proxy template referenced env vars supplied only in an optional overlay; telemetry tests on main failed the next day (B16) — [PR #3570](https://github.com/open-telemetry/opentelemetry-demo/pull/3570)
- Caught by CI on the PR: compose build context changed but GitHub workflow not (B21) — [PR #1386](https://github.com/open-telemetry/opentelemetry-demo/pull/1386)
- Caught through flaky CI months later: consumer offset setting differed between the two consumers (B9) — [PR #3505](https://github.com/open-telemetry/opentelemetry-demo/pull/3505)
- Caught by bug report: webhook registration 400 (C3) — [issue #44](https://github.com/dotnet/eShop/issues/44); event envelope Id lost on consumers (D1) — [issue #667](https://github.com/dotnet-architecture/eShopOnContainers/issues/667); manifests rejected by new Kubernetes (E1) — [issue #802](https://github.com/microservices-demo/microservices-demo/issues/802); Envoy upgrade 503s (B22) — [issue #1800](https://github.com/open-telemetry/opentelemetry-demo/issues/1800); fix lost in rewrite (B20) — [issue #3820](https://github.com/open-telemetry/opentelemetry-demo/issues/3820)
- Caught by later code reading/audit: three consumers misusing `Money.nanos` (B13, B14, B15) — [issue #3742](https://github.com/open-telemetry/opentelemetry-demo/issues/3742); [issue #3747](https://github.com/open-telemetry/opentelemetry-demo/issues/3747); [PR #3752](https://github.com/open-telemetry/opentelemetry-demo/pull/3752)
- Landed deliberately ahead of consumers: Money proto change committed alone, then nine per-service migration commits the same day (A1) — [commit e20ed32](https://github.com/GoogleCloudPlatform/microservices-demo/commit/e20ed325f187a19a150fa05c0cc15a5af9c7a88c); cart env-var rename followed by manifest commits from a different author (A7) — [commit edf1553](https://github.com/GoogleCloudPlatform/microservices-demo/commit/edf1553be99098f70642ea6137878bee08c9e9e9)
- Leftovers after a staged rename: "some leftover names in the docker compose container names and in the test suite" (B6) — [issue #1788](https://github.com/open-telemetry/opentelemetry-demo/issues/1788)

### Inferences
- The 15-of-43 figure is a property of this sample (which favoured discussed PRs), not a base rate for the repositories.
- Verification in these projects is overwhelmingly "run the whole demo and click through an order"; where the reviewer's path differed from the author's (UI vs load generator in B1), the break surfaced. A task environment can reproduce this by having an integration check exercise a path the changing agent does not own.
- Bugs in consumers that compile against the IDL still occur when the contract is semantic (units of `nanos`), and they went unnoticed for years because the only effect was wrong telemetry values.

### Gaps
- Time-to-detection could be established only for B16 (one day) and E1 (fix reported about 19 months after the report); other intervals were not measured.
- No example was found where a protobuf breaking-change linter or consumer-driven contract test caught a break; none of the four priority repos showed such tooling in the threads read.

## What did reviewers and maintainers say about coordination (who needs to be told, ordering, backward compatibility)?

### Takeaway
Explicit coordination talk is sparse and informal: maintainers mention the other repos that must follow (Helm chart, docs), ask for changelog entries, and rely on manual end-to-end testing. The richest written reasoning about contract ownership is the eShopOnContainers debate on whether services should share event types.

### Cited Findings
- Scope warning before a global rename: "Renaming the hipstershop namespace in the protobuf definition will have an effect on all services, and such a change should be taken with proper care." — [OTel issue #638](https://github.com/open-telemetry/opentelemetry-demo/issues/638)
- Who else must change: "Can you add a Chanlog entry for this? Also, we will need to update docs and the Helm chart for this." — [OTel PR #1538](https://github.com/open-telemetry/opentelemetry-demo/pull/1538)
- Rollout ordering across repos: "The Helm chart will only be update with a new release of the demo that should happen after all rename is done" — [OTel issue #1788](https://github.com/open-telemetry/opentelemetry-demo/issues/1788)
- Minimal blast radius for additive change: "Adding a new field should not be requiring regeneration for recommendationservice." — [OB PR #60](https://github.com/GoogleCloudPlatform/microservices-demo/pull/60)
- Backward-compatible default: KAFKA_TOPIC is "defaulting to 'orders' in .env so existing deployments see no behavior change." — [OTel PR #3665](https://github.com/open-telemetry/opentelemetry-demo/pull/3665)
- Backward compatibility by versioning: "The existing V1 API is unchanged and all refactoring is done in a new API version, V2." — [eShop PR #680](https://github.com/dotnet/eShop/pull/680)
- Backward compatibility by negotiation: "That would be a breaking change. If no Accept header is present we default to JSON." — [Loki PR #9813](https://github.com/grafana/loki/pull/9813)
- Serialisation compatibility of persisted events: "we serialize & persist the event data, so OrderStatus would end up being serialized as an int instead of a string by default. How do you want to handle that?" — [eShop PR #151](https://github.com/dotnet/eShop/pull/151)
- Forgotten consumer spotted in review: "I noticed one other place in the codebase that we'll need to change in reaction to the new enum. The orders UI currently sets the status as a CSS class" — [eShop PR #151](https://github.com/dotnet/eShop/pull/151)
- Urgency over process: "I would merge this, even if tests are failing. Without this it just cannot work." — [OTel PR #3570](https://github.com/open-telemetry/opentelemetry-demo/pull/3570)
- Against sharing contracts: "The goal for microservices is that they be self-contained, and not have to be updated based on changes in other projects or services. Thus, some duplication is desirable" — [eSOC issue #724](https://github.com/dotnet-architecture/eShopOnContainers/issues/724)
- For making the dependency explicit: "there IS A REAL AND IMPORTANT dependency between microservices that share integration events ... (it's a contract after all), so I think it's actually good to have that dependency expressed in code somehow" — [eSOC issue #724](https://github.com/dotnet-architecture/eShopOnContainers/issues/724)
- The failure mode named: "If one microservice change an event, get deployed, then publish it. All other microservices subscribed to (relying on) that event will (or could) break." — [eSOC issue #724](https://github.com/dotnet-architecture/eShopOnContainers/issues/724)
- Maintainer's later position: "even though integration events have the same name in different microservices, they have different properties in each one (at least some of them), to handle only the properties each microservice really cares about." — [eSOC issue #724](https://github.com/dotnet-architecture/eShopOnContainers/issues/724)
- Tooling cost of duplicated events: "developers cannot use tooling to find usages of the integration event types." — [eShop issue #19](https://github.com/dotnet/eShop/issues/19)
- Design intent vs consumer expectation: "This is working as currently designed, and has changed with evolutions to the OpenTelemetry specification on how traces should be handled through message queues." — [OTel issue #3357](https://github.com/open-telemetry/opentelemetry-demo/issues/3357)
- Demo-grade reliability acknowledged: "The OTel Demo is a demo and we never had the need to do things the production-ready way." — [OTel issue #4156](https://github.com/open-telemetry/opentelemetry-demo/issues/4156)

### Inferences
- "Who needs to be told" is almost never asked in so many words; it shows up as a checklist item (changelog, docs, Helm chart) or as a reviewer happening to know another consumer. That gap is exactly what a multi-agent task can score: did the changing agent notify each owner of a consumer.
- Three distinct backward-compatibility techniques appear and can each seed a task: default-preserving config (B8), parallel API version (C4), content negotiation (E4).

### Gaps
- No thread was found where maintainers discussed deploy ordering of two services for a single contract change (old producer/new consumer); in monorepo demos everything ships together. Production-project threads (Mimir, Kubernetes, Sentry) would be the place to look and were not covered.

## Are there issues where a bug's root cause spanned two or more services and diagnosis required information from each?

### Takeaway
Yes; eight catalogued cases needed evidence from more than one component, and in three of them the first suspect was wrong. The clearest is OTel #4156, where only the combination of checkout's "success" span and accounting's missing rows shows the loss.

### Cited Findings
- B10: producer reports `messaging.kafka.producer.success = true` and HTTP 200 while "There is no 'Order details' log line and no row in accounting.order"; orders placed about 15 s after broker recovery were also lost until checkout restarted. — [OTel issue #4156](https://github.com/open-telemetry/opentelemetry-demo/issues/4156)
- B9: symptom was missing telemetry from fraud-detection in tests; cause required comparing its consumer config with accounting's and with checkout's low order rate ("~6% of the load generator's task weight"). — [OTel PR #3505](https://github.com/open-telemetry/opentelemetry-demo/pull/3505)
- B22: symptom at load generator and browser; first suspect was the multi-platform build PR ("I'm starting to suspect of the PR #1785"); resolved from frontend-proxy access logs and Envoy release notes, pointing to #1768. — [OTel issue #1800](https://github.com/open-telemetry/opentelemetry-demo/issues/1800)
- B1: load-generator traffic passed while UI traffic panicked the shipping service; needed the shipping log line plus knowledge of what the frontend sent on the quote path. — [OTel PR #587](https://github.com/open-telemetry/opentelemetry-demo/pull/587)
- B16: test failures across the suite traced to one proxy failing bootstrap because of variables defined in a different compose file. — [OTel PR #3570](https://github.com/open-telemetry/opentelemetry-demo/pull/3570)
- B20: a flag slowing images in one component made the load generator's browser click land before hydration, so "the SPA navigation silently no-ops". — [OTel issue #3820](https://github.com/open-telemetry/opentelemetry-demo/issues/3820)
- D4: messages appeared lost when the consumer was offline; actual cause was publisher and consumer configured with the same subscription name, "competing to handle the integration event". A later commenter with similar symptoms on Azure Service Bus was pointed to a different cause (handlers registered after consumption starts). — [eSOC issue #822](https://github.com/dotnet-architecture/eShopOnContainers/issues/822)
- D3: duplicates seen by subscribers; cause in the publisher's outbox query under concurrency. — [eSOC issue #1022](https://github.com/dotnet-architecture/eShopOnContainers/issues/1022)
- C6: wrong diagnosis from reading only the handler; the publish happens in a pipeline behaviour after commit. — [eShop issue #159](https://github.com/dotnet/eShop/issues/159)

### Inferences
- A recurring shape: the producer's own signals say success, the consumer's signals are simply absent, and nothing errors. Tasks built on B9/B10/D4 need each agent to hold only its own logs/config so that neither can diagnose alone.
- Misattribution to a recent unrelated change (B22) is a realistic distractor to plant in a task.

### Gaps
- No example was found of a cross-service bug caused by a permission/scope change or a rate/page-size limit.
- Train Ticket is known for a published fault-injection benchmark, but its GitHub issue tracker yielded no organically reported cross-service bug in the searches run (5 hits, none relevant beyond E2).
