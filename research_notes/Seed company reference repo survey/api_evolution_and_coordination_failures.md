# API evolution, cross-service breaking changes and coordination failures

Research notes compiled 2026-11-11. Evidence labels used throughout: **[EMP]** = empirical study (peer-reviewed or preprint), **[PM]** = primary incident postmortem / investigation report, **[DOC]** = official documentation or specification (normative, not empirical), **[PRAC]** = practitioner opinion or pattern writing. Where I read the primary full text I say "full text"; otherwise the claim rests on an abstract or a search-result summary and is flagged.

---

## 1. What empirical studies exist on API/interface evolution and breaking changes, and what categories and frequencies do they report?

### Takeaway
There is solid empirical work on library APIs (Java) and web/REST APIs, and one directly relevant interview study on microservice API evolution (Lercher et al.). The consistent findings: breaking changes are common (a pooled 27.99% of API changes in 317 Java libraries), most are structural refactorings motivated by new features and simplification, and the hard, under-detected class is *behavioural/semantic* change with an unchanged signature. I found no empirical (repository-mining) study of protobuf/gRPC schema evolution; that area is covered only by normative documentation and tooling.

### Cited Findings

**Microservice API evolution (most directly relevant)**
- [EMP, full text] Lercher, Glock, Macho, Pinzger, "Microservice API Evolution in Practice: A Study on Strategies and Challenges" (arXiv Nov 2023; Journal of Systems and Software; ICSA 2025 journal-first): "17 semi-structured interviews with developers, architects, and managers in 11 companies", identifying "six strategies and six challenges for REpresentational State Transfer (REST) and event-driven communication via message brokers". — [arXiv 2311.08175](https://arxiv.org/abs/2311.08175)
- [EMP] The six strategies (section headings): "Accept necessary breaking changes"; "Stay compatible and avoid unexpected breaking changes" (work around breaking changes; regression test the API; think ahead and design a dynamic API); "Version the API" (new version on breaking changes; expose multiple versions simultaneously); "Collaborate with other teams" (actively involve consumer teams; follow the API-first approach); "Internally, just break (and fix) it"; "Abstract external systems' APIs". — [arXiv 2311.08175](https://arxiv.org/abs/2311.08175)
- [EMP] Reasons for breaking changes, with counts: "a) introducing new functionality (12/17) ... b) improving existing functionality (9/17) ... c) improving the API design (6/17)"; also "bugfixing (4/17), introducing or changing security and authentication techniques (4/17), migrating to a changed external system (4/17), and changes to the underlying infrastructure, e.g., migrating to a new message broker or cloud provider (4/17)". "The participants introduce breaking changes only quarterly to half-yearly to provide enough lead time for affected consumers." — [arXiv 2311.08175](https://arxiv.org/abs/2311.08175)
- [EMP] Structural vs behavioural: "All participants (17/17) considered structural changes, e.g., deletions and renamings, breaking changes. Interestingly, only a few participants (5/17) identified behavioral changes, e.g., changing a timestamp's timezone or returning unexpected values, as harmful and handled them as potential breaking changes." — [arXiv 2311.08175](https://arxiv.org/abs/2311.08175)
- [EMP] Challenge table (participants / companies): "Manual change impact analysis is error-prone 14 / 11" (sub: "Code changes affect the API unexpectedly 9 / 7"; "Understanding consumed APIs' changes is effort 9 / 7"); "Consumers rely on API compatibility 12 / 7"; "Communication with other teams lacks clarity 9 / 7" (sub: "Consumers might be unknown 7 / 5"; "Informal communication channels 17 / 11"; "Communication suffers from hierarchy 6 / 4"); "API maintainability and usability degrade over time 14 / 9" (sub: "Outdated API versions add maintenance overhead 10 / 8"; "Backward compatibility increases technical debt 9 / 6"); "Governmental services are uncooperative 6 / 4"; "Event-driven communication evolution is disregarded 7 / 4". — [arXiv 2311.08175](https://arxiv.org/abs/2311.08175)
- [EMP] Unannounced breaks happen: developers "sometimes overlooked that they introduced breaking changes to the API and published them without versioning or notifications. 'From time to time we face problems, but mainly because some team has overlooked that it has been doing a breaking change' C2-P1." — [arXiv 2311.08175](https://arxiv.org/abs/2311.08175)
- [EMP] Internal APIs are handled differently: "Many participants (11/17) agree that internal breaking changes are easier to implement and integrate ... Many developers (9/17) introducing breaking changes also change all the consumers and the test suites. Some developers (6/17) are in close contact with the colleagues maintaining the consumers, or directly create pull requests for the consumers' source code. ... a few participants (4/17) explicitly stated they do not version internal APIs, but update, test, and redeploy them directly." — [arXiv 2311.08175](https://arxiv.org/abs/2311.08175)
- [EMP] Event-driven evolution: "The asynchronous nature of event-driven communication requires consumers to accept old message versions even after all producers migrated, because old messages might still wait in the queue. Consequently, the participants either migrate all producers and consumers simultaneously and accept potential message loss (3/17), or start implementing their own version negotiation protocol ... (5/17)." (The paper prints "7/19" for the headline count in the prose and "7 / 4" in the table; the "/19" looks like a typo for /17.) — [arXiv 2311.08175](https://arxiv.org/abs/2311.08175)

**Web / REST API evolution**
- [EMP, abstract + secondary] Li, Xiong, Liu, Zhang, "How Does Web Service API Evolution Affect Clients?" (ICWS 2013): five popular web APIs, 256 changed API elements, summarised into 16 change patterns. — [IEEE Xplore](https://ieeexplore.ieee.org/abstract/document/6649592)
- [Secondary listing of the Li et al. patterns, from a PhD notes site] Compile-time breaking: add or remove parameter; change parameter type; change return value type; delete method; rename method; rename parameter; change parameter format; change return value format; change XML tag; combine methods. Listed without a class: split method; expose data; unsupport request method. Run-time breaking: change default parameter value; lower parameter upper bound; restrict API access. — [Cheron, "Evolution space"](https://cheronantoine.gitbook.io/ph-d/api-client-evolution/evolution-space.md)
- [EMP, as cited by Lercher et al.] "Li et al. (2013) stated that more than 80% of web service API changes are refactorings". — [arXiv 2311.08175](https://arxiv.org/abs/2311.08175)
- [EMP, secondary listing] Sohan, Anslow, Maurer, "A Case Study of Web API Evolution" (IEEE SERVICES 2015) adds: move API elements (114 occurrences), rename API elements (31 occurrences), behaviour change with same interface (247 examples), post-condition change, error-condition change. — [Cheron, "Evolution space"](https://cheronantoine.gitbook.io/ph-d/api-client-evolution/evolution-space.md); paper record at [IEEE CS](https://computer.org/csdl/proceedings-article/services/2015/7275a245/12OmNwx3QbE)
- [EMP, full text abstract] Espinha, Zaidman, Gross, "Web API Growing Pains: Stories from Client Developers and Their Code" (CSMR-WCRE 2014): semi-structured interviews with six client developers plus analysis of Twitter, Google Maps, Facebook and Netflix API evolution policies (deprecation periods, breaking-change notification). — [PDF](https://azaidman.github.io/publications/espinhaCSMRWCRE2014.pdf)
- [EMP, as cited by Lercher et al.] Fokaefs and Stroulia (2014) "classified web API changes as no-effect, adaptable, and non-recoverable, representing internal, structural, and behavioral changes, respectively." — [arXiv 2311.08175](https://arxiv.org/abs/2311.08175)

**Library API breaking changes (Java)**
- [EMP, full text] Xavier, Brito, Hora, Valente, "Historical and Impact Analysis of API Breaking Changes: A Large-Scale Study" (SANER 2017): "317 real-world Java libraries, 9K releases, and 260K client applications". Pooled: "501,645 changes were identified, from which 27.99% are breaking changes and 72.01% are non-breaking changes"; by element: Types 11,712 of 61,897 (18.92%), Fields 25,044 of 66,953 (37.41%), Methods 103,704 of 372,795 (27.81%). Per-library distribution: "the first quartile is 0%, the median is 14.78%, and the third quartile is 43.35%". "2.54% of their clients are impacted". — [PDF](https://homepages.dcc.ufmg.br/~mtov/pub/2017-saner-breaking-apis.pdf)
- Note on an apparent conflict: the abstract's "14.78% of the API changes break compatibility" is the per-library median; the 27.99% (often rounded to 28%) is the pooled share. Both come from the same paper. — [PDF](https://homepages.dcc.ufmg.br/~mtov/pub/2017-saner-breaking-apis.pdf)
- [EMP, full text] Brito, Xavier, Hora, Valente, "Why and How Java Developers Break APIs" (SANER 2018): field study of "400 popular Java libraries and frameworks" over 116 days; 282 breaking-change candidates detected; "59 breaking changes, confirmed by the developers of 19 projects". Motivations: "New Feature. With 19 instances (32%)"; "API Simplification. With 17 instances (29%)"; "Improve Maintainability. With 14 instances (24%)". — [arXiv 1801.05198](https://arxiv.org/abs/1801.05198)
- [EMP, abstract] Bogart, Kästner, Herbsleb, Thung, "How to Break an API: Cost Negotiation and Community Values in Three Software Ecosystems" (FSE 2016): multiple case study of Eclipse, R/CRAN and Node.js/npm; "all three ecosystems differ substantially in their practices and expectations toward change and ... those differences can be explained largely by different community values". — [PDF](https://www.cs.cmu.edu/~ckaestne/pdf/fse16.pdf)

**Cross-version data-format incompatibility (closest empirical analogue to schema evolution)**
- [EMP, full text] Zhang et al., "Understanding and Detecting Software Upgrade Failures in Distributed Systems" (SOSP 2021): 123 upgrade failures in 8 distributed systems. Root causes: "incompatible cross-version interaction (63%), broken upgrade operation (33%) misconfiguration (3%), and broken library dependency (2%)". — [PDF](https://www.cs.purdue.edu/homes/yonglezh/pub/upgrade-sosp21.pdf)
- [EMP] Breakdown of the 77 incompatible cross-version interactions (Table 3): syntax — data defined using a serialization library 7, enum 2, system-specific data 41, mishandling of serialization library 6; semantics — incomplete version handling 16, other semantics issue 5. "60% of incompatibility is centered on persistent storage data, while 40% is centered on network messages"; the network-message kind "only manifests during rolling upgrades". — [PDF](https://www.cs.purdue.edu/homes/yonglezh/pub/upgrade-sosp21.pdf)
- [EMP] "The majority (67%) of upgrade failures are catastrophic"; "The majority (63%) of upgrade bugs were not caught before code release"; "Close to 90% of the upgrade failures are deterministic"; "All of the upgrade failures require no more than 3 nodes to trigger"; "Close to two thirds of data semantics incompatibilities are caused by incomplete version checking and handling." The authors' static checker found over 800 cross-version data-format incompatibilities. — [PDF](https://www.cs.purdue.edu/homes/yonglezh/pub/upgrade-sosp21.pdf)

### Inferences
- A defensible top-level split for a change taxonomy, supported by three independent sources (Lercher; Fokaefs and Stroulia; Zhang et al.), is **structural/syntax** (detectable by diffing a schema) versus **behavioural/semantic** (same shape, different meaning). The semantic class is smaller in count (21 of 77 in Zhang et al.) but is the one practitioners under-recognise (5/17 in Lercher).
- The Li et al. run-time-breaking patterns (changed default, tightened bound, restricted access) and the Sohan behavioural patterns (post-condition, error-condition change) are good seeds for "silent" change types that pass a schema diff.
- Zhang et al.'s numbers (deterministic, small-scale, consecutive versions) suggest that a small simulated company with two versions live at once is enough to reproduce most real upgrade-incompatibility failures.

### Gaps
- I found no repository-mining or interview study specifically of protobuf/gRPC/Avro schema evolution in the wild (frequencies of field removal, tag reuse, and so on). One targeted search returned only relational and NoSQL schema-evolution studies and vendor documentation.
- I did not read the full text of Li et al. 2013 or Sohan et al. 2015; their pattern lists come from a secondary source and should be checked before being quoted as verbatim category names.
- Not retrieved: Raemaekers et al. (semantic versioning in Maven), Dig and Johnson (2006), Serbout and Pautasso (ICWE 2023, web API versioning practices; confirmed to exist only), Wang et al. on client reactions to REST API changes.

## 2. What empirical studies exist on microservice failures, faults and anti-patterns, and which fault categories are coordination failures?

### Takeaway
Three studies give usable, numeric fault categories: Zhou et al. (22 industrial microservice faults, 10 of them "Interaction" faults "often caused by missing or incorrect coordination"), Tang et al. (120 cross-system interaction failures whose root cause is a *discrepancy* between two individually correct systems), and Zhang et al. (upgrade failures, section 1). Anti-pattern catalogues (Taibi et al.) and issue taxonomies (Waseem et al.) exist but mostly classify within-service or infrastructure problems; interface-contract coordination is a minority category there.

### Cited Findings

**Zhou et al. — industrial microservice fault cases (Train Ticket)**
- [EMP, full text] Zhou, Peng, Xie, Sun, Ji, Li, Ding, "Fault Analysis and Debugging of Microservice Systems: Industrial Survey, Benchmark System, and Empirical Study" (IEEE TSE 47(2), 2021): "The 16 participants are from 12 companies" and "report 22 fault cases", replicated on the Train Ticket benchmark. — [PDF](https://par.nsf.gov/servlets/purl/10357355)
- [EMP] Category assignment (Table 4): Internal — F9, F14, F18, F19, F21, F22 (functional), F17 (non-functional); Interaction — F1, F2, F6, F7, F8, F10, F11, F12, F13 (functional), F5 (non-functional); Environment — F15, F16, F20 (functional), F3, F4 (non-functional). That is 10 Interaction, 7 Internal, 5 Environment. — [PDF](https://par.nsf.gov/servlets/purl/10357355)
- [EMP] Definition: "The root causes of Interaction faults lie in the interactions among multiple microservices. These faults are often caused by missing or incorrect coordination of microservice interactions." — [PDF](https://par.nsf.gov/servlets/purl/10357355)
- [EMP] The ten Interaction faults, root causes verbatim from Table 3: F1 "Asynchronous message delivery lacks sequence control"; F2 "Different data requests for the same report are returned in an unexpected order"; F5 "The high load of a type of requests causes the timeout failure of another type of requests"; F6 "Endless recursive requests of a microservice are caused by SQL errors of another dependent microservice"; F7 "The overload of requests to a third-party service leads to denial of service"; F8 "The key in the request of one microservice is not passed to its dependent microservice"; F10 "An API used in a special case of BOM updating returns unexpected output"; F11 "The BOM data is updated in an unexpected sequence"; F12 "Price status querying does not consider an unexpected output of a microservice in its call chain"; F13 "Price optimization steps are executed in an unexpected order". — [PDF](https://par.nsf.gov/servlets/purl/10357355)
- [EMP] Environment faults include cross-layer configuration disagreement: F3 "JVM configurations are inconsistent with Docker configurations". — [PDF](https://par.nsf.gov/servlets/purl/10357355)

**Tang et al. — cross-system interaction (CSI) failures**
- [EMP, full text] Tang, Bhandari, Zhang, Karanika, Ji, Gupta, Xu, "Fail through the Cracks: Cross-System Interaction Failures in Modern Cloud Systems" (EuroSys 2023): 120 CSI failures from seven co-deployed open-source systems plus public cloud incidents. "Among 55 cloud incidents, 11 (20%) were caused by CSI failures"; these "lasted from 10 minutes to 19 hours, with a median of 106 minutes". — [PDF](https://tianyin.github.io/pub/csi-failures.pdf)
- [EMP] The central claim: "the root causes of CSI failures are not traditional faults like software bugs and misconfigurations, but are discrepancies." — [PDF](https://tianyin.github.io/pub/csi-failures.pdf)
- [EMP] By plane: "51% of CSI failures in our dataset manifest at the data plane, and 32% of CSI failures manifest at the management plane. Control-plane interactions contribute to 17%" (Control 20, Data 61). — [PDF](https://tianyin.github.io/pub/csi-failures.pdf)
- [EMP] Data plane: "The majority (50/61) of data-plane CSI failures are caused by metadata, namely typical metadata (42/61) such as addresses/names and data schemas, and custom metadata (8/61). The others (11/61) are caused by custom properties and API semantics." "57% (35/61) of data-plane CSI failures are induced by table-related operations." "25% (15/61) data-plane CSI failures are root-caused by data serialization." — [PDF](https://tianyin.github.io/pub/csi-failures.pdf)
- [EMP] Management plane: configuration-induced CSI failures are "mostly about failures of coherently configuring multiple involved systems"; "Parameter-related configuration issues are the majority (21/30)". — [PDF](https://tianyin.github.io/pub/csi-failures.pdf)
- [EMP] Control plane (Table 8, 20 failures): "API semantic violation — Upstream violates semantics of downstream APIs" 13; "State/resource inconsistency — Interacting systems have inconsistent views of the system states or resources" 5; the remainder are feature inconsistencies. "API misuses ... contribute to the majority (13/20) of control-plane CSI failures. The main patterns are implicit semantic violation (8/13) and incorrect invocation context (5/13)." Implicit semantics named: "thread safety, synchrony, ordering". — [PDF](https://tianyin.github.io/pub/csi-failures.pdf)
- [EMP] Fixes: "In 40% (46/115) CSI failures, the merged fixes improve condition checking and error handling instead of repairing the failed interactions." "In 69% (79/115) CSI failures, fixes were applied to code in the upstream system specific to interaction with a downstream system", of which 68 (86%) were in dedicated connector modules. Testing gap: of Spark's integration tests "only 6% of them cross-test dependent systems". "Most (89/120) CSI failures are manifested through crashing behavior." — [PDF](https://tianyin.github.io/pub/csi-failures.pdf)

**Anti-patterns and issue taxonomies**
- [EMP, survey-based; full text] Taibi, Lenarduzzi, Pahl, "Microservices Anti-Patterns: A Taxonomy" (book chapter, arXiv Aug 2019): "a taxonomy of 20 anti-patterns, including organizational (team oriented and technology/tool oriented) anti-patterns and technical (internal and communication) anti-patterns". Table 1.1 (answers #, %, perceived harmfulness 0-10): Hardcoded Endpoints 10, 37, 8; Wrong Cuts 15, 56, 8; Cyclic Dependency 5, 19, 7; API Versioning 6, 22, 6.05; Shared Persistence 10, 37, 6.05; ESB Usage 2, 7, 6; Legacy Organization 2, 7, 6; Local Logging 17, 63, 6; Megaservice 5, 19, 6; Inappropriate Service Intimacy 5, 19, 5; Lack of Monitoring 3, 11, 5; No API-Gateway 4, 15, 5; Shared Libraries 8, 30, 4; Too Many Technologies 3, 11, 4; Lack of Microservice Skeleton 9, 33, 3.05; Microservice Greedy 4, 15, 3; Focus on Latest Technologies 2, 7, 2.05; Common Ownership 4, 15, 2; No DevOps Tools 2, 7, 2; Non-homogeneous adoption 2, 7, 2. — [arXiv 1908.04101](https://arxiv.org/abs/1908.04101)
- [EMP] "API Versioning" anti-pattern definition: "APIs are not semantically versioned"; problem: "In the case of new versions of non-semantically versioned APIs, API consumers may face connection issues. For example, the returning data might be different or might need to be called differently." — [arXiv 1908.04101](https://arxiv.org/abs/1908.04101)
- [EMP, search summary only] Taibi and Lenarduzzi, "On the Definition of Microservice Bad Smells" (IEEE Software 35(3), 2018): 72 developers interviewed, catalogue of 11 microservice-specific bad smells. — [IEEE Computer Society summary](https://publications.computer.org/software-magazine/2018/08/03/definition-microservice-bad-smells-poor-design/)
- [EMP, full text] Waseem et al., "Understanding the Issues, Their Causes and Solutions in Microservices Systems: An Empirical Study" (arXiv 2302.01894; Journal of Systems and Software): 2,641 issues from 15 open-source microservice systems, 15 interviews, survey of 150 practitioners; taxonomy of 19 categories, 54 subcategories, 402 issue types. "Service Execution and Communication Issue (219/2698, 8.11%)", with subcategory "Service Communication (166, 6.15%)" whose majority types are "SERVICE DISCOVERY FAILURE, HTTP CONNECTION ERROR, and GRPC CONNECTION ERROR". Technical Debt is the largest category (687 of 2698). The paper counts 2,698 issue instances across the 2,641 issues. — [arXiv 2302.01894](https://arxiv.org/abs/2302.01894)
- [EMP, abstract] Logical (co-change) coupling between microservices: a metric validated on 145 open-source microservice projects found that "logical coupling affects every system and increases overtime". — [Microservice Logical Coupling: A Preliminary Validation](https://www.research-collection.ethz.ch/entities/publication/6e186438-86d3-4d64-990c-d1496d0cf582); registered-report follow-up at [arXiv 2306.02036](https://arxiv.org/abs/2306.02036)

### Inferences
- The empirical base supports treating "interaction" faults as the plurality in microservice systems (10 of 22 in Zhou et al.), but that study's sample is small and practitioner-recalled, so 45% is indicative only.
- Tang et al.'s framing is the most reusable for an environment: neither side is "buggy" in isolation; the failure is a discrepancy in what each side assumes. That is exactly a coordination failure between owners.
- Retry/idempotency failures are weakly represented in the empirical studies I read (F5 to F7 in Zhou are load and recursion faults, not duplicate-effect faults). Their inclusion in a failure-mode list would rest on documentation and practitioner sources (section 4), not on measured frequency.
- Unit-of-measure mismatches do not appear as a named category in any of the three fault studies; evidence for them is incident-based (section 3).

### Gaps
- I did not retrieve an empirical incident study from a large operator that reports the share of incidents caused by backward-incompatible changes between services (candidates: Microsoft's SoCC 2022 "How to fight production incidents?", HotOS 2019 "What bugs cause production cloud incidents?", SoCC 2016 "Why does the cloud stop computing?"). These exist to my knowledge but were not verified in this session, so no numbers are given.
- The 11 bad smells in Taibi and Lenarduzzi (2018) were not read from the primary text.
- No study was found that measures what share of commits or pull requests in microservice systems span more than one service.

## 3. What do large public postmortems show about cross-service coordination failures?

### Takeaway
Well-documented incidents repeatedly show the same shape: one party changes or produces something that is valid by its own lights, and another party consumes it under an unstated or unenforced assumption (units, identifier type, field count, row uniqueness, non-null fields, flag meaning, "zero means zero"). In several cases a written interface specification existed and was not followed or not checked.

### Cited Findings

Instead, the data was reported in English units of pound-seconds (lbf-s). ... Further candidates from a curated collection (one-line descriptions as given by the collection; individual reports not read):
- CircleCI, Nov 2021: a deploy changed a PostgreSQL field's type so old and new rows conflicted with a downstream component's strict schema validation. — [incident report](https://discuss.circleci.com/t/incident-report-november-8-2021-jobs-stuck-in-a-not-running-state/41890)
- CircleCI, May 2021: a RabbitMQ upgrade applied a consumer acknowledgement timeout to all queue types although the changelog described it as limited to quorum queues. — [postmortem](https://discuss.circleci.com/t/postmortem-may-21-2021-delay-in-starting-docker-jobs-machine-remote-docker-environments-blocked/40274)
- Heroku, Jun 2023: a foreign key used a smaller integer type than the primary key it referenced and overflowed. — [status page](https://status.heroku.com/incidents/2558)
- GitHub, Aug 2024: a configuration change altered how database hosts answered a routing service's health checks. — [availability report](https://github.blog/news-insights/company-news/github-availability-report-august-2024/)
- TUI Boeing 737 (UK AAIB): after a reservation-system upgrade the title "Miss" was interpreted as a child, so the load sheet understated mass (an enum/semantic mismatch between systems). — [AAIB report](https://assets.publishing.service.gov.uk/media/604f423be90e077fdf88493f/Boeing_737-8K5_G-TAWG_04-21.pdf)
- Collection index: [danluu/post-mortems](https://github.com/danluu/post-mortems)

### Inferences
- Recurring structural features across these incidents: (a) the contract was implicit or unenforced at the boundary (Atlassian API "assumes the input is correct"; Cloudflare's unfiltered query; MCO's unaudited SIS); (b) tests exercised only the compatible subset (CrowdStrike's wildcard in field 21; Google's code path not exercised during regional rollout); (c) impact was delayed relative to the change (Google 2020 grace period, October to December; CrowdStrike template type released months before the triggering instance), which breaks the link between change and failure; (d) the consumer failed hard instead of degrading (panic, crash loop).
- Three of the eight are "internal producer treated as trusted": Cloudflare's own remediation is to validate internally generated configuration like user input. For an environment this suggests rewarding consumer-side validation of producer output, not only producer-side notification.
- Knight and Google 2020 are both "contract" phase failures of an expand/contract migration: old meaning left live while the new meaning was deployed.

### Gaps
- I found no public postmortem from a major operator that explicitly names a protobuf or Avro schema-incompatible change with a not-yet-updated consumer as root cause. One targeted search returned only vendor guides and personal blog anecdotes, which I did not include as evidence.
- The SEC Knight Capital order was not retrieved directly (the direct fetch failed); quotes are via a secondary blog reproducing the order's paragraphs. The order's exact date and the $12 million penalty reported by news outlets were not verified against the primary.
- The Stripe RCA and the curated-collection entries were not read in full.
- Classic non-software interface incidents often cited in this context (Ariane 5 flight 501, the "Gimli Glider" fuel-units error) were not researched in this session.

## 4. What practices are documented for preventing these, and what does each require the two sides to communicate?

### Takeaway
Every documented practice reduces to making one side's assumptions explicit and machine-checkable before deployment, plus an agreed ordering of who moves first. The documentation is normative, not empirical: I found no controlled evidence on how much any of these practices reduces incidents. Lercher et al. is the only empirical source on usage, and it reports that communication around changes is ad hoc in all 11 companies studied.

### Cited Findings

**Consumer-driven contract testing (Pact)** [DOC]
- "Contract testing is a technique for testing an integration point by checking each application in isolation". "Pact is a code-first consumer-driven contract testing tool". — [Pact docs](https://docs.pact.io/)
- "Each pact is a collection of interactions", each with "An expected request - describing what the consumer is expected to send to the provider" and "A minimal expected response - describing the parts of the response the consumer wants the provider to return." "Provider verification passes if each request generates a response that contains at least the data" described. Provider states "allow you describe the preconditions on the provider required to generate the expected response." Limits: "Contract tests should focus on the messages (requests and responses) rather than the behaviour." — [How Pact works](https://docs.pact.io/getting_started/how_pact_works)
- Deployment gate: `can-i-deploy` checks the "Pact Matrix" ("the grid created when you create a table of all the consumer and provider versions" tested against each other) for a successful verification between the candidate version and every integrated application version already in the target environment; requires publishing verification results and recording each deployment (`record-deployment`). — [can-i-deploy](https://docs.pact.io/pact_broker/can_i_deploy)
- **Consumer tells provider**: the exact requests it sends and the minimum response fields and types it relies on, per provider state. **Provider tells consumer**: verification result per consumer version. **Both tell the broker**: which version is deployed where.

**Schema registry and compatibility modes (Confluent)** [DOC]
- "`BACKWARD`: consumer using schema `X` can process data produced with schema `X` or `X-1`"; "`FORWARD`: data produced using schema `X` can be read by consumers with schema `X` or `X-1`"; "`FULL`: backward and forward compatible between schemas `X` and `X-1`"; transitive variants check "against all previously registered schemas"; "`NONE` compatibility type means schema compatibility checks are disabled." "The default compatibility mode is BACKWARD." — [Confluent schema evolution](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)
- Rollout order is part of the contract: under BACKWARD, "upgrade all consumers before you start producing new events"; under FORWARD, "first upgrade all producers to using the new schema"; under FULL, "you can upgrade the producers and consumers independently." — [Confluent schema evolution](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)
- "best practice for Protobuf is to use BACKWARD_TRANSITIVE, as adding new message types is not forward compatible." "JSON Schema does not explicitly define compatibility rules". — [Confluent schema evolution](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)
- **Communicated**: the schema itself (registered centrally), the agreed compatibility mode per subject, and therefore which side upgrades first.

**Avro schema resolution** [DOC]
- "fields are matched by name"; if the writer has a field the reader lacks, "the writer's value for that field is ignored"; if the reader has a field with a default that the writer lacks, "the reader should use the default value from its field"; if the reader's field has no default and the writer lacks it, "an error is signalled". Enums: "if the writer's symbol is not present in the reader's enum and the reader has a default value, then that value is used, otherwise an error is signalled." Promotions: "int is promotable to long, float, or double"; "long is promotable to float or double"; "float is promotable to double"; "string is promotable to bytes"; "bytes is promotable to string". — [Avro 1.11.1 specification](https://avro.apache.org/docs/1.11.1/specification/)
- **Communicated**: the writer's schema must be available to the reader; defaults carry the compatibility burden.

**Protobuf compatibility rules** [DOC]
- Unsafe: "Changing field numbers for any existing field is not safe." "Moving fields into an existing `oneof` is not safe." Safe: "Adding new fields is safe." ("old binaries simply ignore the new field when parsing"); "Removing fields is safe" provided "The same field number must not used again"; "Adding additional values to an enum is safe." Conditionally compatible: "`int32`, `uint32`, `int64`, `uint64`, and `bool` are all compatible" (with truncation); "`string` and `bytes` are compatible as long as the bytes are valid UTF-8"; singular to repeated is "**not** generally safe for numeric types". — [proto3 language guide](https://protobuf.dev/programming-guides/proto3/)
- Best-practice headings: "Don't Re-use a Tag Number"; "Do Reserve Tag Numbers for Deleted Fields"; "Don't Change the Type of a Field"; "Don't Change the Default Value of a Field"; "Don't Go from Repeated to Scalar"; "Don't Add a Required Field"; "Do Include an Unspecified Value in an Enum"; "Do Reserve Numbers for Deleted Enum Values"; "Don't use Text Format Messages for Interchange"; "Never Rely on Serialization Stability Across Builds"; "Do Use Different Messages For RPC APIs and Storage"; "Don't Use Booleans for Something That Has Two States Now, but Might Have More Later". — [Proto best practices](https://protobuf.dev/best-practices/dos-donts/)
- Tooling categories (Buf): `FILE` (default) "Detects changes that move generated code between files, breaking generated source code on a per-file basis"; `PACKAGE` "Detects changes that break generated source code changes on a per-package basis"; `WIRE_JSON` "Detects changes that break wire (binary) or JSON encoding"; `WIRE` "Detects changes that break wire (binary) encoding". Example rules: `FIELD_NO_DELETE`, `FIELD_SAME_TYPE`, `FIELD_SAME_NAME`, `ENUM_VALUE_NO_DELETE`, `RPC_SAME_REQUEST_TYPE`. — [Buf breaking rules](https://buf.build/docs/breaking/rules/)

**API compatibility policy (Google AIP-180, approved; created 2019-07-23)** [DOC]
- Three kinds of compatibility. Source: "Code written against a previous version must compile against a newer version". Wire: "Code written against a previous version must be able to communicate correctly with a newer server." Semantic: "Code written against a previous version must continue to receive what most reasonable developers would expect." — [AIP-180](https://google.aip.dev/180)
- Rules (paraphrased from the AIP): components must not be removed or renamed within a major version; field types must not change even when wire-compatible; do not move fields into or out of a oneof; resource names must not change; default values and the format of existing field values must not change; adding pagination with a smaller default page size is breaking for older clients. — [AIP-180](https://google.aip.dev/180)

**API versioning and deprecation (Stripe; practitioner account, 5 Aug 2017)** [PRAC]
- "Fields that were present before should stay present, and fields should always preserve their same type and name." "it's safe to add a new API endpoint, or a new field to an existing API endpoint that was never present before." On first request an account "is automatically pinned to the most recent version available"; per-request override via the `Stripe-Version` header. Each backwards-incompatible change is encapsulated in a version change module that "defines documentation about the change, a transformation, and the set of API resource types" affected. Stripe states it "maintained compatibility with every version of our API since the company's inception in 2011." — [Stripe blog, "APIs as infrastructure: future-proofing Stripe with versioning"](https://stripe.com/blog/api-versioning)
- [EMP] In Lercher et al., all 17 participants version their APIs and many "provide multiple API versions allowing consumers to migrate at their own pace"; the cost is the challenge "Outdated API versions add maintenance overhead" (10 participants). — [arXiv 2311.08175](https://arxiv.org/abs/2311.08175)
- **Communicated**: provider declares which change classes it will never make inside a version; consumer declares (or is assigned) the version it depends on; provider announces lead time before removal ("quarterly to half-yearly" in Lercher).

**Expand/contract (parallel change)** [PRAC]
- Danilo Sato, 13 May 2014: "Parallel change, also known as expand and contract, is a pattern to implement backward-incompatible changes to an interface in a safe manner". Expand: "you augment the interface to support both the old and the new versions"; Migrate: "you update all clients using the old version to the new version"; Contract: "remove the old version". Caveat: if the contract phase is never done "you might end up in a worse state than you started". — [martinfowler.com, ParallelChange](https://martinfowler.com/bliki/ParallelChange.html)
- **Communicated**: provider signals "new form available"; each consumer signals "migrated"; provider must know the full consumer set before contracting (which Lercher reports is often unknown: "Consumers might be unknown", 7/17).

**Idempotency keys (Stripe API reference)** [DOC]
- "A client generates an idempotency key, which is a unique key that the server uses to recognize subsequent retries of the same request." For API v1, "Stripe saves the status code and body of the first request made with a given idempotency key after endpoint execution begins. Retries with the same key return the saved response, including `500` errors." Keys can be removed "after they're at least 24 hours old". "The idempotency layer compares incoming parameters to those of the original request and errors if they're not the same". "all `POST` requests accept idempotency keys"; `GET` and `DELETE` are "idempotent by definition." — [Stripe API reference](https://docs.stripe.com/api/idempotent_requests)
- **Communicated**: client supplies the key and commits to resending identical parameters; server documents the retention window and which operations are safe to retry.

**Design/API review and collaboration** [EMP for usage; PRAC for prescription]
- [EMP] "Most participants collaborate with dependent teams by discussing the planned API changes before implementation. They focus on the API definition before implementing the underlying functionality in parallel" (the "API-first approach"). But on notification: "We could not identify a generalizable strategy to inform consumer teams about API changes. The participants (17/17) either follow their own ad hoc strategy or accept the overhead for manual communication." Consumer discovery methods reported: implicit knowledge of colleagues or managers (8/17), tracing or logging of REST calls (6/17), authentication credentials (4/17), manually maintained lists (3/17). — [arXiv 2311.08175](https://arxiv.org/abs/2311.08175)
- [PRAC, secondary notes on the book] Google's large-scale-change process (the Rosie tool) splits a cross-cutting change into shards that are each independently testable and approved by the owning team's reviewers. — [Software Engineering at Google, ch. 22](https://abseil.io/resources/swe-book/html/ch22.html)

**Summary: what each practice makes the two sides exchange**

| Practice | Provider/producer must communicate | Consumer must communicate | Shared artefact |
|---|---|---|---|
| Consumer-driven contracts | Verification results; provider states supported | Requests sent; minimal response relied on | Pact file, broker matrix, deployment records |
| Schema registry | New schema, before producing | (implicitly) schema version it reads with | Subject plus compatibility mode, which fixes upgrade order |
| Protobuf/Avro rules | Reserved numbers/names; defaults | Tolerance of unknown fields/symbols | The schema file and a breaking-change check in CI |
| Versioning and deprecation | Change class, version identifier, sunset date | Pinned version; migration status | Changelog, version header |
| Expand/contract | "Both forms live now"; "old form removed on date" | "Migrated" | Consumer inventory |
| Idempotency keys | Retention window; replay semantics | Key; identical parameters on retry | Header convention |
| API-first/design review | Proposed interface before implementation | Use cases, objections | Interface definition document |

### Inferences
- Structural compatibility is fully mechanisable (Buf, schema registry, Pact); semantic compatibility is defined in AIP-180 only by a "reasonable developers would expect" standard, and Pact explicitly scopes itself to messages, not behaviour. So the practices leave the semantic class (units, defaults, ordering, meaning of zero or null) to human communication, which matches where the incidents in section 3 cluster.
- Rollout order is not a separate practice but a consequence of the compatibility direction chosen (BACKWARD: consumers first; FORWARD: producers first). A cross-service change type should therefore carry a "who must move first" attribute.
- Every practice presupposes the provider knows its consumers. Lercher's finding that consumers are often unknown and tracked informally is the weakest link, and is something a simulated company can vary deliberately.

### Gaps
- No empirical evaluation was found of the effectiveness of contract testing, schema registries or expand/contract at reducing incidents.
- Not retrieved: Stripe's current versioning and deprecation policy pages, Google AIP-181/185 (stability levels, versioning), Zalando or Microsoft REST guidelines, the IETF `Deprecation`/`Sunset` headers, and any primary write-up of zero-downtime database migrations using expand/contract.
- The Confluent page was only read to character 100,000 of about 173,000.

## 5. What does research on human software teams say about coordination needs across module/service boundaries?

### Takeaway
The classical finding (Cataldo and Herbsleb) is that work items whose technical dependencies are matched by actual coordination between the people involved are resolved faster and fail less, and that "logical" (co-change) dependencies matter more than syntactic call dependencies. Organisational structure predicts failure-proneness strongly at Microsoft, and cross-site work takes about 2.5 times longer. However, a 2021 large-scale replication on 25 open-source projects found no relationship between congruence and bugs or churn, so effect size and generality are contested.

### Cited Findings
- [EMP, search summary] Cataldo, Herbsleb, Carley, "Socio-technical congruence: a framework for assessing the impact of technical and work dependencies on software development productivity" (ESEM 2008): when developers' coordination patterns were congruent with their coordination needs, modification-request resolution time was significantly reduced; logical dependencies among software modules had far more impact than call or data dependencies. — [ACM DOI record](https://www.springerprofessional.de/doi/10.1145/1414004.1414008)
- [EMP, abstract read in full text] Cataldo and Herbsleb, "Coordination Breakdowns and Their Impact on Development Productivity and Software Failures" (IEEE TSE 2013), two large projects from two companies: "the gaps between coordination requirements and the actual coordination activities carried out by the developers significantly increased software failures. Our analyses also showed that higher levels of congruence are associated with improved development productivity." — [PDF](https://par.nsf.gov/servlets/purl/10038372)
- [EMP, full-text abstract] Counter-evidence: Mauerer, Joblin, Tamburri, Paradis, Kazman, Apel, "In Search of Socio-Technical Congruence: A Large-Scale Longitudinal Study" (IEEE TSE; arXiv May 2021): "based on an analysis of 25 large open-source projects, ... STMC is not related to project quality measures—software bugs and churn—in any temporal scenario. That is, we find no statistical relationship between the alignment of developer tasks and developer communications on the one hand, and project outcomes on the other hand." — [arXiv 2105.08198](https://arxiv.org/abs/2105.08198)
- [EMP, full text (technical-report version)] Nagappan, Murphy, Basili, "The Influence of Organizational Structure on Software Quality: An Empirical Case Study" (ICSE 2008; MSR-TR-2008-11): on Windows Vista, organisational metrics predicted failure-prone binaries with "average precision across all 50 random splits ... 0.87" and "average recall value ... 0.84", "significantly higher than using traditional metrics like churn, complexity, coverage, dependencies, and pre-release bug measures". — [Microsoft Research TR](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-2008-11.pdf)
- [EMP, search summary] Herbsleb and Mockus, "An Empirical Study of Speed and Communication in Globally Distributed Software Development" (IEEE TSE 29(6), 2003): distributed work items "appear to take about two and one-half times as long to complete as similar items where all the work is colocated". — [PDF](https://www.st.cs.uni-saarland.de/edu/empirical-se/2006/PDFs/herbsleb03.pdf)
- [EMP, search summary] Conway's law / mirroring: MacCormack, Baldwin, Rusnak, "Exploring the duality between product and organizational architectures: A test of the 'mirroring' hypothesis" (Research Policy 41(8), 2012): "In all of the pairs we examine, the product developed by the loosely coupled organization is significantly more modular than the product from the tightly coupled organization"; differences "up to a factor of six, in terms of the potential for a design change in one component to propagate to others". — [Harvard DASH](https://dash.harvard.edu/handle/1/34403525)
- [EMP] Microservice-specific: Lercher et al. name the resulting problem "tight organizational coupling" and report "Communication suffers from hierarchy" (6 participants, 4 companies) and reliance on individuals' implicit knowledge of who consumes an API ("He just remembers most of the time"). — [arXiv 2311.08175](https://arxiv.org/abs/2311.08175)
- [EMP, abstract] Ecosystem-level negotiation of change costs differs by community values (Eclipse, CRAN, npm). — [Bogart et al., FSE 2016](https://www.cs.cmu.edu/~ckaestne/pdf/fse16.pdf)
- [EMP, slides/record only] Ma, Chen, Zhang, Zhou, Xu, "How do developers fix cross-project correlated bugs? A case study on the GitHub scientific Python ecosystem" (ICSE 2017): 271 pairs of cross-project correlated bugs involving 204 projects; studies root-cause tracking across project boundaries and downstream/upstream coordination. — [ICSE 2017 record](https://bibtex.github.io/ICSE-2017-MaCZZX.html)
- [EMP, search summary] Code review: Bacchelli and Bird, "Expectations, Outcomes, and Challenges of Modern Code Review" (ICSE 2013, Microsoft): finding defects is the top stated motivation, but defect-related comments are a small proportion of outcomes; the main benefits are knowledge transfer, team awareness and alternative solutions; "code and change understanding is the key aspect of code reviewing". — [ICSE 2013 programme entry](https://2013.icse-conferences.org/content/expectations-outcomes-and-challenges-modern-code-review.html); [TU Delft repository record](https://repository.tudelft.nl/record/uuid:d629803b-bbec-4593-a7f2-6f4b2266ff5a)
- [EMP] Integration testing rarely crosses system boundaries: only 6% of Spark's integration tests cross-test dependent systems. — [Tang et al., EuroSys 2023](https://tianyin.github.io/pub/csi-failures.pdf)

### Inferences
- The best-supported operational definition of a "coordination need" is Cataldo's: two people need to coordinate when their tasks touch artefacts that are dependent, with co-change history a better dependency signal than static calls. In a multi-agent environment this can be computed exactly (which services a change's correct completion depends on) and compared with which agents actually communicated, giving a congruence metric with a published lineage.
- Because the 2021 replication found no effect in open-source projects, congruence should be reported as a diagnostic, not assumed to be a proxy for outcome quality.
- Code review evidence suggests review is weak at catching defects generally and depends on the reviewer understanding the change; a reviewer who owns a different service lacks that context. I found no study that directly measures review's catch rate for cross-component issues, so this is an inference.

### Gaps
- No direct empirical source was retrieved on code review catching (or missing) cross-component or cross-service interface issues.
- Not retrieved: de Souza et al., "Sometimes You Need to See Through Walls" (CSCW 2004, on APIs as coordination barriers); Kraut and Streeter (1995) on coordination in software development; Bird et al. on ownership; the ESEM 2008 effect sizes for resolution time.
- Several findings in this section rest on abstracts or search summaries, as flagged.

## 6. Is there a published taxonomy of cross-service change types or coordination structures to reuse?

### Takeaway
There is no single published taxonomy of "cross-service change types" that covers both the technical change and the coordination it requires. There are, however, several partial taxonomies that are well established and compose cleanly: change-pattern lists for web APIs, the three compatibility kinds in AIP-180, the Buf rule categories, the syntax/semantics and persistent/transient dimensions of Zhang et al., the plane and discrepancy classification of Tang et al., the Interface Evolution Patterns for provider policy, and Malone and Crowston's dependency types for coordination structure. Reusing and combining these is better supported than inventing categories.

### Cited Findings
- **What changed (interface level)**: Li et al.'s 16 web API change patterns and Sohan et al.'s behavioural additions (lists in section 1). — [IEEE Xplore](https://ieeexplore.ieee.org/abstract/document/6649592); [secondary listing](https://cheronantoine.gitbook.io/ph-d/api-client-evolution/evolution-space.md)
- **How it breaks (compatibility kind)**: source / wire / semantic. — [AIP-180](https://google.aip.dev/180). Machine-checkable levels FILE / PACKAGE / WIRE_JSON / WIRE. — [Buf](https://buf.build/docs/breaking/rules/). Client-impact classes "no-effect, adaptable, and non-recoverable" (Fokaefs and Stroulia, as cited). — [arXiv 2311.08175](https://arxiv.org/abs/2311.08175)
- **Where the incompatibility lives**: persistent data vs transient network messages; syntax vs semantics; with sub-kinds serialization-library data, enum, system-specific data, version handling. — [Zhang et al., SOSP 2021](https://www.cs.purdue.edu/homes/yonglezh/pub/upgrade-sosp21.pdf)
- **Which interaction plane and discrepancy**: data plane (metadata: addresses/names, schemas; custom properties; API semantics; serialization), management plane (coherent multi-system configuration; monitoring), control plane (API semantic violation; state/resource inconsistency; feature inconsistency). — [Tang et al., EuroSys 2023](https://tianyin.github.io/pub/csi-failures.pdf)
- **Fault location**: Internal / Interaction / Environment, crossed with Functional / Non-functional. — [Zhou et al., TSE 2021](https://par.nsf.gov/servlets/purl/10357355)
- **Provider evolution policy (pattern language)**: Version Identifier; Semantic Versioning; Two in Production; Aggressive Obsolescence; Experimental Preview; Limited Lifetime Guarantee; Eternal Lifetime Guarantee. — [Microservice API Patterns, evolution category](https://microservice-api-patterns.org/patterns/evolution/); source paper Lübke, Zimmermann, Pautasso, Zdun, Stocker, "Interface Evolution Patterns: Balancing Compatibility and Extensibility across Service Life Cycles" (EuroPLoP 2019), [record](https://eprints.cs.univie.ac.at/6082). These are practitioner patterns "mined from public Web APIs and industry projects", not measured frequencies.
- **Team strategies and challenges**: the six strategies and six challenges of Lercher et al. (section 1) are the only empirically grounded list specific to microservice teams. — [arXiv 2311.08175](https://arxiv.org/abs/2311.08175)
- **Coordination structures (general theory)**: Malone and Crowston, "The Interdisciplinary Study of Coordination" (ACM Computing Surveys 26(1), 1994) define coordination as "the process of managing dependencies among activities" and analyse processes for "managing shared resources, producer/consumer relationships, simultaneity constraints, and task/subtask dependencies". — [Crowston's page](https://crowston.syr.edu/node/54); [PDF](https://crowston.syr.edu/sites/default/files/acmcs94.pdf)
- **Organisational anti-patterns**: Taibi et al.'s split into organisational (team; technology/tool) and technical (internal; communication) anti-patterns. — [arXiv 1908.04101](https://arxiv.org/abs/1908.04101)

### Inferences
A composite taxonomy that stays within published categories could label each cross-service change on these axes:

1. **Interface kind**: synchronous API (REST/gRPC); asynchronous event/message; shared persistent data; shared configuration or flags; shared library. (Lercher covers the first two; Zhang's persistent/transient split and Taibi's Shared Persistence and Shared Libraries cover the rest.)
2. **Change pattern**: add / remove / rename / retype / reformat / split or combine / change default / tighten constraint / restrict access / change behaviour, post-condition or error condition (Li; Sohan).
3. **Compatibility kind broken**: none / source / wire / semantic (AIP-180), which determines whether tooling can detect it.
4. **Who must move first**: consumers first (backward-compatible) / producers first (forward-compatible) / either (full) / lockstep (none) (Confluent).
5. **Coordination dependency type**: producer/consumer; shared resource; simultaneity; task/subtask (Malone and Crowston).
6. **Provider policy in force**: Two in Production, Aggressive Obsolescence, Limited or Eternal Lifetime Guarantee, Experimental Preview (Lübke et al.).

A matching failure-mode list, each with an anchor in sections 1 to 3: unannounced structural break; silent semantic change (units, timezone, default, meaning of zero or blank); unknown or forgotten consumer; wrong rollout order or mixed-version window; incomplete contract phase (old meaning left live, repurposed flag); queued old-format messages after migration; implicit ordering/synchrony assumption violated; incoherent cross-service configuration; identifier-type confusion between teams; consumer trusts internal producer output without validation; tests cover only the compatible subset; delayed manifestation that decouples change from failure.

### Gaps
- No published taxonomy was found that jointly classifies a cross-service change and the communication acts it requires; the composite above is my synthesis, not a cited scheme.
- I did not verify the primary text of Malone and Crowston beyond the abstract, nor the Lübke et al. paper beyond the pattern website; Thompson's pooled/sequential/reciprocal interdependence and the Team Topologies interaction modes are other candidate coordination-structure schemes that were not researched.
- Koçi et al. and other "classification of changes in API evolution" papers may offer a more formal REST change classification; not retrieved.
